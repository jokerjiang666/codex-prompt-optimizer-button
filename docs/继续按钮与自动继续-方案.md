## 1. 现状与代码事实（已实测）

### 1.1 悬浮按钮
- `OverlayWindow.xaml`：`StackPanel` 内当前只有 `UndoButton`（撤回）与 `OptimizeButton`（星芒）。
- `OverlayWindow.xaml.cs:99`：`Width = visible ? 60 : 30;` —— 窗口宽度随按钮数量变化，右边缘锚定在「目标」芯片右侧 + 9px，加按钮时向左侧扩展，不会破坏已修复的重叠问题。
- 浮层是 `WS_EX_NOACTIVATE`：点击浮层不会抢走 Codex 的前台焦点。

### 1.2 轮询状态机（MainController）
- 350ms 一轮：找输入框 → 读草稿文本 → 会话标识 → `IsGenerationInProgress` → 权限锚点。
- `IsGenerationInProgress` 靠 UIA 找名为 `停止 / 停止回答 / 停止生成 / stop / stop generating` 的按钮。
- 已有草稿清空判定（`draft=cleared` / `draft=sent`），用于隐藏撤回按钮和记录最近发送。

### 1.3 关键缺口：目前没有「发送」能力
- `ComposerAdapter` 只有 `ReadText / CanWrite / WriteText`（`ValuePattern.SetValue`），**没有任何触发发送的代码**。
- 实测 UIA（当前 Codex 窗口）：输入框同一行按钮为
  `添加文件等内容`(947,1450) / `更改权限`(996,1450) / `deepseek-flash 高`(1720) / `听写`(1931) / **`加入队列`(1985,1450,43x42)**。
  → 生成进行中时发送键叫「加入队列」；空闲时预期为「发送」。**发送键名称会随状态变化**，必须做白名单 + 位置判定。

### 1.4 报错在 UIA 中的形态（实测）
- 会话区文本是一个个 `Text` 元素（当前 152 个），带 `Name` 与 `BoundingRectangle`，可按 Y 坐标定位到「输入框上方的尾部区域」。
- 因此错误行（如截图那行）可以作为 `Text.Name` 被读到并匹配，不需要截图 OCR。

## 3. 手动「继续」按钮设计

### 3.1 UI
- 顺序：`[撤回] [优化] [继续]`（2026-09-20 调整：继续按钮改到优化按钮右侧；撤回出现时位于最左）。
- 复用 `IconButtonStyle`（28x28、悬停底 #E8EBE7、圆角 11）；图标 18x18，与现有 Viewbox 同网格（256 画布）。
- 宽度：30（只有优化）/ 60（+继续）/ 90（+撤回）。右边缘锚定不变；「继续」为最右一个按钮，紧邻目标芯片。
- 悬停提示（ToolTip）：「继续（发送“继续”）」。

### 3.2 点击行为（新增发送能力）
1. 找输入框；不可写 → 提示「请先打开 Codex 输入框」。
2. **输入框非空 → 不覆盖**，提示「输入框已有内容」并中止（避免吞掉用户草稿）。
3. `WriteText("继续")`。
4. 找发送按钮并 `InvokePattern.Invoke()`：
   - 名称白名单：`发送 / Send / 加入队列 / 排队 / Submit / 提交`；
   - 位置约束：与「更改权限」同一行、位于模型芯片右侧、窗口右半边；
   - 若同时命中多个，取最右侧且可用的那个。
5. **发送校验**：1.5s 内输入框应变为空；为空 → 成功（并刷新撤回/最近记录逻辑）；未清空 → 提示「发送失败，请手动回车」并记日志（不重复尝试）。
6. 兜底（仅在上面失败时）：`SetFocus` 到输入框 + `SendInput` 回车（Codex 需为前台；否则不做）。

> 说明：不做「先写再等用户回车」的半成品，否则用户会以为已经发送。

## 4. 自动检测中断并继续

### 4.1 触发时机（性能红线）
- **只在 `generationInProgress` 由 true → false 的那一次**做一次错误扫描（不是每 350ms 全树扫描），保护此前已做的 UIA 轮询优化。
- 每次扫描加 1s 冷却，扫描范围限定为「输入框上方 ~600px 的会话尾部文本元素 + 按钮元素」。

### 4.2 判定信号（三路取或）
1. **错误文本特征**（大小写不敏感，子串匹配）：
   - 英文：`exceeded retry limit`、`429 too many requests`、`too many requests`、`rate limit`、`network error`、`connection error`、`stream error`、`connection reset`、`request timed out`、`timeout`、`failed to fetch`
   - 中文：`重试次数已用完`、`超出重试上限`、`请求过于频繁`、`网络错误`、`连接中断`、`请求失败`、`响应中断`、`服务异常`
   - 结构：`last status: 429`、`status: 5xx`
2. **错误旁的「重试 / Retry」按钮**存在。
3. 会话尾部出现错误图标 + 错误文案组合（实现时用一次真实 429 现场 dump UIA，确认元素类型后固化规则）。

### 4.3 幂等、冷却与停止条件

- **单轮幂等**：一次「生成中 → 空闲」的状态翻转只触发一次自动继续，避免同一错误被重复发送。
- **冷却间隔**：两次自动继续之间 ≥ **10 秒**（可配置）。
- **无次数上限**：按最新决定不做次数上限；只要开关开启且再次检测到中断，就会继续发送。
- **停止条件**（任一满足即停止）：
  1. 用户在设置里关闭「自动检测中断并发送」；
  2. 用户手动发送任意消息（视为用户已接管）；
  3. 切换会话/窗口（重置本轮状态）。
- **前置条件**：开关开启 + 会话可写 + 输入框为空 + 会话身份未变 + 当前不是生成中。
- **不触发**：用户自己点「停止」造成的中断（没有错误特征）。

> ⚠️ 无上限的代价：如果 Codex 一直返回 429，程序会每 10 秒自动重发一次，可能持续消耗额度。日志会记录累计触发次数；需要停时关掉开关即可。状态机预留「软上限 / 熔断」扩展点，后续要加只是几行判断。

### 4.4 日志（沿用 runtime-status.log）

```

autocontinue=skipped reason=draft-not-empty
autocontinue=skipped reason=cooldown remainMs=4300
```

## 8. 验收标准

1. 手动：点「继续」→ 输入框出现设定的发送内容 → 自动发送 → 输入框清空、开始生成。
2. 手动：输入框已有内容时点「继续」→ 不覆盖、给出提示。
3. 自动：开关默认关闭；关闭时行为与现在完全一致。
4. 自动：开启后遇到 `exceeded retry limit, last status: 429 Too Many Requests` → 10 秒内自动发送设定内容。
5. 自动：同一轮生成只触发一次；两次触发间隔 ≥10 秒；**无次数上限**，连续报错会持续重试，直到关闭开关或用户接管。
6. 设置：把发送内容改成别的文本（如「继续，不要停」）后，按钮与自动继续都发送新内容；留空回退「继续」。
7. 设置：关闭「显示悬浮窗的『继续』按钮」后，悬浮窗只剩优化按钮（宽度 30），重新打开后恢复。
8. 不回归：撤回、优化、最近发送、右键菜单外部关闭、锚点位置全部不变。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 错误文案种类多 | 特征表 + 结构信号（重试按钮）；未命中的新错误记日志便于补充 |
| 发送按钮名称随状态变化 | 名称白名单 + 同行位置约束 + 发送后清空校验 |
| 自动继续放大配额消耗（429 且无上限） | 默认关闭 + 10 秒冷却 + 日志累计计数 + 一键关闭开关；预留软上限扩展点 |
| 误判把用户正文当错误 | 只扫描会话尾部 + 只在生成结束瞬间 + 单轮幂等 |
| 自定义内容为空或超长 | 保存时 Trim，空值回退「继续」，最多 200 字符 |
| UIA 遍历拖慢 UI | 仅在状态翻转时扫描；文本/按钮快照短 TTL 复用 |
